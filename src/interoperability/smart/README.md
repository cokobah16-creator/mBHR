# SMART on FHIR: prepared, not exposed

This folder holds the groundwork for a future SMART App Launch 2.x authorization server in front of the `/fhir/R4` gateway: the types for client registration, the authorization request, the token response and launch context (`types.ts`), and two pure functions, `parseSmartScope` and `intersectScopes`, that parse SMART v1 and v2 scopes and compute the granted set as requested x client-allowed x user-permitted (x consent), never wider than any of them (`scopes.ts`, tested in `__tests__/scopes.test.ts`). The design these pieces serve is [docs/interoperability/smart-auth-design.md](../../../docs/interoperability/smart-auth-design.md); the Phase 1 plan it builds on is [docs/interoperability/smart-auth.md](../../../docs/interoperability/smart-auth.md).

Nothing here is wired to any route, imported by the gateway, or able to issue or accept a token. `/oauth/authorize`, `/oauth/token` and `/.well-known/smart-configuration` are intentionally **not** served: there is no authorization server, and publishing a discovery document for one would advertise capabilities that do not exist, so there is no placeholder or fake `smart-configuration` endpoint either (`/fhir/R4/.well-known/smart-configuration` answers 404). `SMART_ENABLED` and `SMART_EXTERNAL_CLIENTS_ENABLED` are refused by the gateway configuration (`readFhirConfig()` fails and every request gets a 503) until the blockers listed in the design document are resolved.
